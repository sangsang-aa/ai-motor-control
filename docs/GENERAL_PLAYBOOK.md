# 软件项目架构、作业流程与 Agent 开发要领（通用版）

> **版本**：1.0
> **日期**：2026-11-06
> **分支说明**：本分支只包含本文档，不包含任何项目源码；第 5 章“参考实现”中的文件路径指向主项目分支。
> **适用范围**：Web / 桌面 / 上位机 / 工具类项目；尤其适合“UI + 实时设备/外部服务 + AI Agent”这类系统。
> **使用方式**：把本文当作模板。第 1–4 章是通用方法，第 5 章给出一个参考实现（MOTOTUNE Web）作为落地示例。
> **原则**：通用方法可复制，领域细节必须按项目替换；不要照搬示例中的协议、参数和路径。

## 0. 一页速览

### 0.1 三条主线

| 主线 | 解决的问题 | 本文位置 |
|---|---|---|
| 架构设计 | 系统怎么分层、模块怎么隔离、数据怎么流、安全边界在哪 | 第 1 章 |
| 作业流程 | 从需求到上线的标准步骤、分支/测试/文档/发布 | 第 2 章 |
| Agent 开发要领 | AI Agent 如何安全、可验证地参与开发；如何开发 Agent/LLM 功能 | 第 3 章 |

### 0.2 五条硬规则

1. **先读后写**：不读懂现有代码、测试、协议，不提案、不改代码。
2. **先提案后编码**：讲清逻辑、影响文件、测试方案，拿到明确批准再动手。
3. **模块隔离**：一次只改“拥有该职责”的模块；跨模块先出干涉报告。
4. **功能必有测试**：没有对应测试的改动不算完成；mock 不能替代实机验收。
5. **不碰密钥/不破坏历史**：密钥不入库；共享分支不 force push、不擅自改写历史。

### 0.3 交付物

代码 + 测试 + 文档 + 交接说明 + 可复现的验证证据。

## 1. 架构设计

### 1.1 设计目标

| 目标 | 含义 | 验收问题 |
|---|---|---|
| 可测试 | 核心逻辑不依赖 UI/硬件 | 能否在无设备、无网络时跑单测？ |
| 可替换 | 外部依赖可换实现 | 串口/网络/LLM 能否用 mock 替换？ |
| 可观测 | 状态、错误、事件可追踪 | 出问题时能否定位到模块/命令/参数？ |
| 安全 | 越权/误操作/泄露有边界 | 最坏情况下会不会伤设备/泄密钥？ |
| 可移植 | Web/桌面/不同部署可迁移 | 换运行环境要改多少层？ |
| 可交接 | 新人能按文档接手 | 有没有架构图、文件地图、流程与验收清单？ |

### 1.2 分层模型

推荐五层。层数可按项目缩减，但**依赖方向必须单向**。

```text
L1 Presentation       页面 / 组件 / 视图
        ↓
L2 Interaction        状态管理 / 事件总线 / hooks / 表单
        ↓
L3 Domain             用例 / 校验 / 状态机 / 协议语义
        ↓
L4 Adapter            串口 / gRPC / HTTP / LLM / 数据库 / 文件
        ↓
L5 Platform           Browser / Node / Electron / 设备
```

| 层 | 职责 | 允许依赖 | 禁止 |
|---|---|---|---|
| L1 表现层 | 布局、交互、可视化 | L2、L3 的只读接口 | 直接开串口/ sockets/数据库 |
| L2 交互/状态 | 单一状态源、事件订阅、派生值 | L3、L4 接口 | 反向 import UI |
| L3 领域层 | 纯逻辑、校验、状态机、用例 | L4 接口/类型 | 依赖 DOM、React、具体传输 |
| L4 适配层 | 协议编解码、连接、重试 | L5、外部库 | 依赖 UI/状态 |
| L5 平台层 | 浏览器/Node/Electron/设备 | 系统 API | 业务规则 |

**依赖规则**

- 依赖只能向下，不能反向。
- 共享契约（类型/常量/错误码）放在中立模块。
- 适配层实现接口；领域层只依赖接口，不依赖具体实现。
- 测试通过替换适配层实现来隔离硬件/网络。

### 1.3 模块边界

为每个模块写清“拥有什么、暴露什么、禁止什么”。

| 模块 | 拥有 | 对外接口 | 不得越界 |
|---|---|---|---|
| 示例：设备通信 | 帧/CRC/连接/心跳/遥测 | `connect/send/close` + 事件 | UI 不直接操作传输 |
| 示例：业务状态 | 会话/设备状态/缓存 | store/selector | 不 import 组件 |
| 示例：外部服务 | 请求/重试/错误映射 | service interface | 不写业务规则 |
| 示例：AI/LLM | 工具定义/确认/审计 | tool registry + events | 不直接执行硬件命令 |
| 示例：持久化 | 本地存储/迁移 | repository | 不持有 UI 状态 |

**接口优先**

```ts
// 领域层只认接口
interface DeviceAdapter {
  connect(): Promise<void>
  send(command: Command): Promise<Ack>
  onTelemetry(cb: (sample: Sample) => void): () => void
  close(): Promise<void>
}
```

- Web Serial、Electron IPC、TCP、mock 都实现同一接口。
- 换实现不改 UI/领域逻辑。

### 1.4 数据流模式

| 模式 | 适用 | 关键点 |
|---|---|---|
| 请求/响应 | LLM 调用、保存、查询 | 超时、错误映射、取消 |
| 流式 | SSE/日志/大响应 | 分帧、背压、中断、结束标记 |
| 事件总线 | 高频遥测、跨模块广播 | 类型安全、退订、异常隔离 |
| 命令/ACK | 设备控制 | 单命令在途、序号、重试、STOP 优先 |
| 轮询 | 低频状态/无推送接口 | 间隔、重叠保护、失败退避 |
| 持久化 | 设置/会话/文件 | 单一来源、版本、迁移 |

**选择原则**

- 有明确因果关系 → 请求/响应。
- 持续产生、多个消费者 → 事件总线。
- 有副作用、需要确认 → 命令/ACK + 人工确认。
- 外部不支持推送 → 轮询；必须防重入。

### 1.5 状态与持久化

- **单一状态源**：同一事实只存一处；其他为派生值。
- **明确生命周期**：内存 / 会话 / 本地持久 / 服务端。
- **Schema 版本**：持久化结构必须有版本号与迁移策略。
- **敏感数据**：密钥不落日志、不进代码、不进 Git；本地存储也要评估风险。
- **大对象**：不要把大文本/图片塞进消息历史；存引用/ID，按需取。

| 数据 | 建议存储 | 备注 |
|---|---|---|
| 会话/设置 | localStorage / IndexedDB / DB | 版本 + 迁移 |
| 高频采样 | 内存环形缓冲 | 不持久化 |
| 文件/附件 | IndexedDB / 对象存储 | 存元数据 + Blob |
| 密钥 | 服务端 env / 系统钥匙串 | 避免前端明文长期保存 |

### 1.6 可靠性与错误处理

| 机制 | 用途 | 注意 |
|---|---|---|
| 超时 | 防止永久等待 | 每层都要有 deadline |
| 重试 | 瞬时故障 | 必须幂等；同序号重发 |
| 去重 | 重复包/重复命令 | seq/idempotency key |
| 熔断/退避 | 持续失败 | 避免雪崩 |
| 看门狗 | 设备/连接失联 | 自动停机/释放 |
| 降级 | 部分能力不可用 | 明确提示，不伪造成功 |
| 错误分类 | UI/日志/告警 | 用户可读 vs 诊断详情 |

**错误对象建议**

```ts
type AppError = {
  code: string          // 稳定错误码
  message: string       // 用户可读
  detail?: unknown      // 日志/诊断
  retryable: boolean
  cause?: unknown
}
```

### 1.7 安全设计

| 风险 | 机制 |
|---|---|
| 误操作设备 | 允许列表、范围 clamp、二次确认、急停 |
| AI 越权 | 工具白名单、参数锁、写操作需人工确认 |
| 密钥泄露 | 服务端代理、env/钥匙串、日志脱敏、Git 扫描 |
| 网络 SSRF | host 校验、私网限制、超时、禁止公网暴露 |
| 注入 | 不把用户输入拼进命令；结构化参数 |
| 审计 | 记录谁在何时执行了什么命令/参数/结果 |

**最小权限**：Agent 只能调用完成当前任务所需的工具；写操作与读操作分离。

### 1.8 可测试性

```text
        E2E / 手工验收       少、慢、覆盖关键路径
      Integration            mock 外部边界
    Unit                     多、快、纯逻辑
```

| 层 | 测试方式 | 例子 |
|---|---|---|
| 纯逻辑 | 单测 | 帧/CRC、校验、解析、状态机 |
| 适配层 | 集成测试 | fake serial / fake gRPC / mock HTTP |
| UI | E2E | 关键交互、错误态、下载 |
| 硬件/实机 | 人工验收 | 真实设备、真实网络、真实模型 |

**可测试性设计**

- 核心逻辑与 DOM/传输解耦。
- 提供确定性 demo/fake 模式。
- 稳定的 `data-testid` / 无障碍标签。
- 时间/随机/网络可注入。
- mock 只替代边界，不替代业务逻辑。

### 1.9 可观测性

- **结构化日志**：时间、模块、命令、参数、结果、耗时、错误码。
- **事件流**：状态变化可回放；关键命令有审计。
- **健康状态**：连接、队列、最后心跳、错误计数。
- **指标**：成功率、延迟、重试次数、丢包。
- **脱敏**：密钥、token、个人信息不入日志。

### 1.10 可移植性

- 把“只能在某环境运行”的代码收敛到 L4/L5。
- 服务端边界明确：浏览器不能开的 TCP/gRPC 放 Node/主进程。
- 配置外置：env / 设置面板 / 配置文件，不写死。
- 静态导出与 Server 路由的取舍提前决策。
- 桌面封装时优先替换适配器，而不是重写 UI。

### 1.11 架构决策记录（ADR）

每个关键决策写一条 ADR，避免后人反复争论。

```markdown
## ADR-<编号>：<标题>

- 状态：提议 / 接受 / 废弃
- 日期：
- 背景：
- 决策：
- 备选方案：
- 后果（好/坏）：
- 迁移/回滚：
```

## 2. 作业流程

### 2.1 流程总览

```text
需求 intake
  → 只读侦察
  → 变更提案
  → ⏸ 明确批准
  → 建分支
  → 实现（scope lock）
  → 测试（unit/integration/e2e/实机）
  → 文档
  → 评审/验收
  → 提交/推送/PR
  → 交接
```

### 2.2 需求 intake

先把需求变成可验收的句子：

```markdown
## 需求
<用户原话/目标>

## 验收标准
- [ ] <可观察行为 1>
- [ ] <可观察行为 2>

## 不做
- ...

## 约束
- 兼容性 / 性能 / 安全 / 设备 / 时间
```

- 复述需求，不改意思。
- 明确“不做”，防止范围膨胀。
- 有歧义先问，不猜。

### 2.3 只读侦察

至少读：

1. 项目总览（`AGENTS.md` / README / 架构文档）。
2. 目标模块的代码与测试。
3. 协议/接口文档。
4. 现有同类实现（沿用模式）。
5. `git status` / 当前分支 / 最近提交。

只读命令：`grep/rg`、`sed`、`git log`、跑现有测试。

### 2.4 变更提案

```markdown
## 提案：<一句话标题>

**需求原文**：<复述>

**模块归属**：<层/模块>

**逻辑**：
1. ...
2. ...

**改动文件**：
- ...

**数据流/接口**：
- ...

**测试**：
- 单测：...
- 集成：...
- E2E：...
- 实机：...

**风险/兼容**：...

**不做**：...
```

提案必须让评审者能判断“逻辑对不对、范围对不对、测试够不够”。

### 2.5 批准 gate

- 只有明确批准（“批准/可以/继续/开始/OK/go”）才进入实现。
- 沉默、模糊同意不算批准。
- 批准后范围锁定；新发现 → 停止，重新提案/干涉报告。

### 2.6 分支与提交

| 类型 | 分支名 | 提交前缀 |
|---|---|---|
| 功能 | `feat/<topic>` | `feat(scope): ...` |
| 修复 | `fix/<topic>` | `fix(scope): ...` |
| 文档 | `docs/<topic>` | `docs: ...` |
| 杂项 | `chore/<topic>` | `chore: ...` |

- 一个提交一个主题。
- 不混入格式化、无关重构、生成产物。
- 不提交密钥/本地配置/构建缓存。
- 共享分支不 force push；需要改写历史必须明确批准。
- 新分支首次推送：`git push -u origin <branch>`。

### 2.7 实现

- **Scope lock**：只改提案列出的文件。
- **最小 diff**：不重构、不美化、不顺手优化。
- **沿用模式**：命名、目录、状态管理、样式、错误处理跟现有代码一致。
- **不新增依赖**：除非提案批准。
- **不留垃圾**：无调试日志、注释死代码、TODO 占位。
- **类型安全**：避免 `any`/`@ts-ignore`；错误要可读。
- **兼容**：迁移/回滚/旧数据要考虑。

### 2.8 测试

| 改动类型 | 最低验证 |
|---|---|
| 纯逻辑 | 单测（边界/错误/回归） |
| 适配器/协议 | 单测 + fake server/集成 |
| UI | E2E 关键路径 + 错误态 |
| 跨模块 | 全量单测 + 全量 E2E + build |
| 硬件/网络 | mock + 实机验收清单 |

**规则**

- Bugfix：先写失败回归测试，再修。
- 不删除/skip 失败测试来“变绿”。
- mock 通过 ≠ 实机通过；验收记录写设备/版本/环境。
- 报告写命令、通过数量、未验证项。

### 2.9 文档

| 变更 | 更新 |
|---|---|
| 新功能/流程 | 用户手册 / 功能交接 |
| 新文件/目录/导出 | 文件结构文档 |
| 协议/参数 | 协议文档 |
| 测试/验收 | 测试文档 |
| 架构/决策 | ADR / 架构文档 |
| 目录树/约束 | `AGENTS.md` 或等价知识库 |

文档要能回答：怎么跑、怎么测、怎么改、出问题怎么查。

### 2.10 评审/验收

**代码评审清单**

- [ ] 逻辑符合提案；范围未膨胀。
- [ ] 依赖方向正确；没有跨层直连。
- [ ] 错误/超时/重试/取消处理完整。
- [ ] 安全边界（校验/锁/确认/脱敏）到位。
- [ ] 测试覆盖正常/边界/错误。
- [ ] 文档同步；无密钥/本地配置。

### 2.11 发布/回滚

```text
install → typecheck → unit → integration/e2e → build → smoke → release
```

- 发布前确认服务端路由/环境变量/权限。
- 回滚优先 `revert`；共享分支不用 `reset --hard`。
- 数据库/配置变更要有向前/向后兼容方案。

### 2.12 DoR / DoD

**Definition of Ready**

- 需求/验收标准明确。
- 模块归属与影响面清楚。
- 测试策略与实机条件明确。
- 依赖/权限/数据已就绪。

**Definition of Done**

- 代码 + 测试 + 文档完成。
- 类型检查/单测/E2E/build 通过（或明确说明未跑原因）。
- 无密钥/本地配置/构建产物入库。
- 交接说明与已知限制已写。

## 3. Agent 开发要领

> 本节有两个含义：**A. Agent 作为开发者**（AI 怎么改代码）；**B. 开发 Agent/LLM 功能**（怎么给产品加 AI 能力）。

### 3.1 Agent 作为开发者

#### 3.1.1 角色

| 角色 | 职责 |
|---|---|
| Planner | 读需求、侦察、拆任务、写提案 |
| Implementer | 按批准范围实现 |
| Tester | 设计/运行测试，给证据 |
| Reviewer | 查逻辑/边界/安全/回归 |
| Doc/Handoff | 更新文档、交接 |

小任务可一人多角色，但**提案/实现/验收**三个阶段不能省。

#### 3.1.2 硬规则

| # | 规则 |
|---|---|
| H1 | 无明确批准不写文件/不改配置/不删文件 |
| H2 | 先讲逻辑再写代码 |
| H3 | 一次只改职责所属模块 |
| H4 | 功能必须有对应测试 |
| H5 | 跨模块先出干涉报告 |
| H6 | 不删除/skip 失败测试来“变绿” |
| H7 | 不碰密钥/不绕安全约束 |
| H8 | 不读代码不臆测 |

#### 3.1.3 工作循环

```text
Recon（只读）
  → Propose
  → ⏸ Wait for approval
  → Implement（scope lock）
  → Verify（tests/build）
  → Report（evidence）
```

中途发现新事实/必须跨模块 → 停止，重新提案或出干涉报告。

#### 3.1.4 上下文获取

- 先读项目知识库/架构文档，再读代码。
- 用搜索定位现有实现，不凭空造新风格。
- 读测试了解契约与边界。
- 查 `git status/log`，确认没有覆盖他人未提交工作。
- 不确定就问；不要用猜测补全。

#### 3.1.5 工具使用

- 文件编辑用精确替换；大改先备份/确认。
- shell 命令只读优先；破坏性命令先确认。
- 不并行跑会争同一构建目录的任务（如 build 与 dev server）。
- 网络/安装依赖/权限提升要说明理由。
- 临时文件放约定临时目录，不污染仓库。

#### 3.1.6 安全与隐私

- 不读取/打印/提交密钥；发现泄露先报告并建议轮换。
- 检查 `.gitignore`、历史提交、构建产物。
- 不把本地路径/用户名/主机信息写进公共文档。
- 不擅自 force push / 改写历史 / 删除分支。
- 不执行来源不明的脚本。

#### 3.1.7 沟通

- 提案：目标、逻辑、文件、测试、风险、不做。
- 进度：简短；遇到阻塞立即说明。
- 完成：改了什么、测试命令/数量、构建结果、未验证项。
- 不夸大：mock 通过就说 mock 通过，不说“实机通过”。

#### 3.1.8 交接

- 更新架构/文件/测试/协议文档。
- 写清已知限制、未完成项、下一步。
- 保留可复现命令与环境要求。
- 交接文档按“功能”和“文件位置”两个维度组织更易查。

#### 3.1.9 反模式

| 反模式 | 后果 |
|---|---|
| 不读代码直接改 | 破坏契约/回归 |
| 顺手重构 | 扩大影响面，难评审 |
| 删除失败测试 | 掩盖问题 |
| 硬编码密钥/地址 | 泄露/不可移植 |
| 伪造成功/吞错误 | 线上事故 |
| 并行 build + dev | 假失败/缓存损坏 |
| force push 共享分支 | 丢失他人提交 |
| 文档不更新 | 交接失败 |

### 3.2 开发 Agent / LLM 功能

#### 3.2.1 工具（Tool）设计

每个工具都是一份“对外 API 合同”：

```ts
type Tool = {
  name: string                 // 稳定、动词开头
  description: string          // 何时用/不用
  inputSchema: JSONSchema      // 强类型、范围、单位
  sideEffect: 'read' | 'write' // 读写分离
  requiresConfirmation: boolean
  idempotent: boolean
  timeoutMs: number
  errorCodes: string[]
}
```

规则：

- **窄接口**：一个工具只做一件事；不要“万能执行器”。
- **强类型/范围/单位**：RPM、A、V、ms 写清楚；越界拒绝。
- **读写分离**：读操作可自动；写操作默认需确认。
- **幂等/去重**：写操作要有 idempotency key 或序号。
- **最小权限**：Agent 只能调用当前任务需要的工具。
- **错误可读**：返回稳定错误码 + 用户可读信息。
- **可审计**：记录参数、结果、耗时、确认人。

#### 3.2.2 Prompt / 系统提示

- 角色：你是谁、能做什么、不能做什么。
- 工具策略：何时调用、何时先问、何时拒绝。
- 安全约束：禁止绕过锁/范围/确认。
- 输出格式：结构化/简洁/中文或英文。
- 失败策略：工具失败时如实报告，不伪造。
- 防注入：用户内容不能覆盖系统规则；敏感操作必须确认。

#### 3.2.3 Human-in-the-loop（HITL）

推荐状态机：

```text
idle → pending（收到 tool_call）
     → executing（用户确认）
     → idle（成功/失败/取消）
pending → idle（超时/忽略）
```

- 锁：同一时间只允许一个待确认写操作。
- 确认卡：展示工具名、参数、影响、超时。
- 超时：自动取消并解锁。
- 审计：记录确认/忽略/执行结果。
- 读操作（如状态查询）可免确认，但要有白名单。

#### 3.2.4 上下文与检索

- 预算：文本/图片/token 上限；超出截断并提示。
- 引用：保留来源/文件名，便于追溯。
- 隐私：不上传未授权文件；敏感内容脱敏。
- 大对象：不要每轮塞进消息历史；存 ID/引用，按需取。
- 失败降级：检索失败 → 不带上下文继续，并提示。

#### 3.2.5 安全与对抗

- 工具白名单 + 参数校验 + 范围 clamp。
- 写操作二次确认；危险操作 dry-run。
- 速率限制/并发限制。
- 提示注入防护：外部文档视为不可信数据。
- 密钥不进入 prompt/日志/工具返回。
- 紧急停止/一键回滚。

#### 3.2.6 评估

| 层级 | 内容 |
|---|---|
| 单测 | 参数解析、工具 schema、错误映射 |
| 集成 | fake tool/fake server，验证调用链 |
| E2E | 用户确认/忽略/超时/失败 |
| 对抗 | 越权/注入/超范围/恶意输入 |
| 人工 | 真实任务成功率、可解释性、可恢复性 |

- 保留 golden prompts / 回归用例。
- 记录模型/提示/工具版本，便于比较。
- 评估不只看“能答”，还要看“该拒绝时拒绝”。

#### 3.2.7 可观测性

- 工具调用：名称、参数摘要、结果、耗时、错误码。
- 用户覆盖：确认/忽略/修改。
- 性能：首 token、总时长、重试。
- 安全：越权尝试、锁冲突、异常频率。

#### 3.2.8 发布

- 新工具/提示先灰度/开关。
- 保留旧行为回滚路径。
- 变更记录写清模型/提示/工具版本。

### 5.1 分层映射

| 通用层 | 参考实现 |

### 5.2 关键决策

- 页面客户端渲染；服务端仅两个 Node 路由。
- 浏览器不能开 TCP/gRPC → TekHSI 走 `/api/tekhsi`。

- 事件总线 + zustand，避免 prop drilling。
- 硬件全部 mock 进 CI；实机单独验收。
- 主题用 `--cx-*` 双 token；默认亮。
- 安全：6000 RPM clamp、AI 参数锁、工具确认、急停。
